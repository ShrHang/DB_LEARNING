# 第一阶段测试方案与用例

状态：M1—M5及第5轮删除扩展已由用户验收。删除用例见[第17节](#survey-deletion-tests)，实际执行证据见[第18节](#survey-deletion-results)，本轮用户确认与交接见[第19节](#survey-deletion-acceptance)。M6已规划，待本轮提交后执行；此次文档整理不算复测。需求依据见[requirements](requirements.md)，接口依据见[api](api.md)。

## 1. 分层与工具

| 层次 | 测什么 | 建议工具 | 数据库 |
| --- | --- | --- | --- |
| 单元测试 | 答案校验、操作符、规则优先级、最终路径、定义校验 | node:test + node:assert/strict | 不需要 |
| HTTP 集成测试 | 注册登录、权限、管理、提交、匿名、事务、聚合 | node:test + Supertest agent + 原生 MongoDB 驱动 | 真实单节点副本集 |
| 页面验收 | 逐题交互、上一题、回填、过期恢复、提交结果、统计页面 | 先使用明确的手工步骤 | 独立验收数据库 |

使用 Node.js 自带测试运行器减少框架依赖；Supertest agent 用于发送 HTTP 并保持各账号 Cookie。[Node.js 测试文档](https://nodejs.org/api/test.html)、[Supertest 官方说明](https://github.com/forwardemail/supertest)是工具依据。

不以 mock 数据库替代唯一索引、事务或聚合验证。时间采用业务时钟依赖控制，确定性并发可使用测试装配的 Promise 闸门；它们只控制时序，实际查询仍落到 MongoDB。第一阶段无需先引入浏览器自动化平台；后续若手工回归成本明显增加再评估。

## 2. 创建顺序与目录

1. 从需求提取场景，为每个场景写好输入、步骤和独立的预期结果。
2. 实现共享函数时同步编写相应单元测试。
3. 实现接口时同步增加真实数据库集成测试，不等到 M6 才开始测试。
4. 每个里程碑完成时执行相关测试；M6 执行完整回归与页面验收，填写实际结果。

以下为业务测试目录规划；M2/M3 已创建账号、数据库、问卷管理/定义校验及公共 helpers，其他测试随模块创建，不建立空文件：

```text
tests/
  unit/
    validation.test.js
    rules.test.js
    path.test.js
    definition.test.js
  integration/
    auth.test.js
    surveys.test.js
    submissions.test.js
    concurrency.test.js
    statistics.test.js
  fixtures/
    surveys.js
    answers.js
  helpers/
    test-db.js
    auth-agent.js

```

每个测试采用“准备数据 → 调用功能 → 断言结果”，测试名称带本文件编号。例如 `I08 同一请求并发重试只保存一份答卷`。期望值来自需求或手工演算，不能调用被测统计/规则函数生成期望值。

## 3. 测试环境和公共步骤

- 单元测试可独立运行。集成测试必须连接支持事务的真实副本集，启动前检查拓扑和必要索引。
- 每个测试套件创建唯一的 `questionnaire_test_<随机标识>` 数据库，记录本次创建的名称，结束时仅清理本次测试数据库。清理程序拒绝开发/业务数据库名。
- 创建 Express app 与监听端口分离，HTTP 测试装配 app、业务时钟及测试数据库。每个测试/套件隔离状态，不依赖其他用例先运行。
- 各账号使用独立 agent。公共登录步骤：GET CSRF token → 注册或准备账号 → 登录 → 取得新 token → 后续写请求附带 Cookie 和新 token。
- 数据断言包括实际文档数量、版本、冻结标记、答案内容与响应字段。会话等辅助写入不计入答卷数量。
- 初期集成套件串行运行，避免清理和索引初始化互相干扰；并发场景在单个用例内发起多个独立请求，每个请求使用自己的数据库事务。
- 测试结束关闭 app 使用的监听器、会话 store 和数据库连接；不得依靠强制退出掩盖未释放资源。

M2 已安装依赖并提供以下脚本（实现命令以 [package.json](../package.json) 为准）：

```json
{
  "test:unit": "node --test --test-isolation=none tests/unit/*.test.js",
  "test:integration": "node --test --test-isolation=none --test-concurrency=1 tests/integration/*.test.js",
  "test": "npm run test:unit && npm run test:integration"
}
```

数据库连接使用独立测试配置。驱动和 Supertest 的实际版本已在 M2 锁定；环境与启动命令见 [README](../README.md)。可选 Chromium 检查见 npm run test:browser，无额外浏览器框架依赖。

## 4. 固定数据

### 4.1 身份与隔离

至少准备作者 author_A、其他作者 author_B、填写者 user_1/user_2/user_3，均使用专用测试账号。表中的 Q1、A、X 等是逻辑别名；fixture 工厂负责生成合法稳定 ID，不把别名误当作必须通过 UUID 格式检查的真实值。

### 4.2 路径问卷 S_path

- Q1：必答文本，默认进入 Q2。
- Q2：必答单选；A → Q3，B → Q4。
- Q3：必答单选，仅选项 Back；选择后回到 Q2。
- Q4：必答文本，最后一题，默认 END。

交互路径 `Q1 → Q2(A) → Q3(Back) → Q2(B) → Q4 → END` 的最终有效路径是 `[Q1,Q2,Q4]`。Q3 即使曾填写且为必答，也不提交、不计数。

### 4.3 统计问卷 S_stats

依次包含单选 A/B/C、可选多选 X/Y/Z、可选数字、可选文本；无跳转。匿名模式 optional，样例账号均可合法提交。

| 答卷 | 单选 | 多选 | 数字 | 文本 |
| --- | --- | --- | --- | --- |
| 1 | A | X、Y | 10 | 清晰 |
| 2 | B | Y | 20 | 方便 |
| 3 | A | 空 | 空 | 空 |

手工预期：总答卷数 3；单选 A=2、B=1、C=0，有效回答3；多选 X=1、Y=2、Z=0，有效回答2，百分比50%、100%、0%；数值有效回答2、平均值15；文本非空明细2条。浮点百分比采用合理误差比较，例如误差不超过 1e-9，不先四舍五入再断言。

数值0另用独立样例 `[0,10]`，均值5；不修改上述基线数据，以免用例互相影响。

## 7. 关键用例的可复现时序

### 7.1 同请求并发与响应丢失（I09）

1. 准备已发布问卷、合法答案和同一登录账号，记录答卷数0。
2. 用同一个requestId和相同负载，同时发起两个独立HTTP请求。
3. 检查至少一次为新增成功，另一次为成功重放，二者submissionId相同；数据库恰好一份。
4. 将这份成功响应视为客户端未收到，用原负载重试，预期200、原ID、数量仍1。
5. 关闭问卷后再次重试，仍返回原成功结果；随后同key修改一个答案，预期409冲突，数量不变。

该测试用客户端丢弃响应模拟结果未知，仍实际执行提交。不能把第二次提交 mock 成成功来证明幂等。

### 7.2 首份事务回滚（I10）

1. 准备contentLocked=false、firstSubmittedAt=null的已发布问卷，记录revision。
2. 在测试装配的插入调用处注入明确失败，保证此次尝试不能被自动重试后成功；已执行的数据库写入仍使用真实事务。
3. 发起合法首份提交，等待失败返回和事务结束。
4. 查询真实数据库，断言答卷0份、锁定与首次时间未改变、revision未留下冻结更新。
5. 移除故障并重新提交，预期仅一份答卷且冻结字段同步出现。

故障入口只存在于测试装配，不作为生产HTTP接口，也不修改真实业务数据库。

### 7.3 关闭前已受理（I13）

1. 使用已存在首份答卷、已冻结且允许多次填写的问卷，记录原数量n。
2. 测试闸门暂停一份新请求：事务已读取开放状态并受理，但尚未插入；随后由作者完成关闭。
3. 释放请求，预期该已受理请求可完成，答卷数n+1；关闭后的另一份新请求409，数量仍n+1。
4. 首份提交与关闭导致事务冲突/重试的场景单独验证：回滚后的新尝试重新受理，不能沿用旧开放状态。

采用闸门而非固定sleep控制先后；闸门须设置测试级超时并在清理中释放，避免失败用例挂住整个套件。
